# 技術選定

- **対象**：Akiko Portfolio（個人ポートフォリオサイト）
- **作成日**：2026-10-01
- **状態**：下書き。実装済みの構成をコードから書き起こしたもの。選定理由は本人が確認して確定する（§6）

## 1. 選定方針

優先順位（上ほど優先）：

1. **課題要件（MUST）を満たすこと**（Next.js App Router／Express／Prisma／PostgreSQL／Firebase 認証）
2. **仕組みを自分の言葉で説明できること**（就職活動で見せるため、動くだけでなく理由を話せる構成にする）
3. **秘密情報をブラウザへ渡さないこと**（DB 接続情報・内部 API キー・Firebase Admin の認証情報はサーバー側だけで扱う）
4. **無料枠で公開し続けられること**（閲覧頻度が低くても止まらない、または自動で復帰する）
5. **作品が増えてもコードを書き換えずに運用できること**（管理画面から登録・並び替え）

## 2. 技術スタック一覧

区分の意味：**課題指定**＝課題要件で決まっていたもの／**選択**＝自分で選んだもの／**予定**＝これから導入するもの。

| レイヤ | 採用技術（バージョン） | 区分 | このアプリでの役割 | 選定理由 |
| ------ | ---------------------- | ---- | ------------------ | -------- |
| 言語 | TypeScript 5（フロント・バック共通、`strict: true`） | 課題指定 | 全コード | 型で入力値やAPIレスポンスの取り違えを実装中に検出できる |
| 実行環境 | Node.js 24 | 選択 | Next.js・Express の実行 | README に記載のバージョン。リポジトリ内では未固定（§4） |
| フロントエンド | Next.js 16.2（App Router）＋ React 19.2 | 課題指定 | 公開画面、管理画面、サーバー処理（Server Component／Server Action／Route Handler） | ブラウザと Express の間に Next.js のサーバー機能を挟めるため、秘密情報をブラウザへ渡さずに済む |
| CSS | Tailwind CSS 4 | 選択 | 画面のスタイル | （§6 で確認） |
| バックエンド | Express 5.2 | 課題指定 | 公開 API、管理 API、画像 API、入力チェック | フロントと分離した API サーバーとして、役割の境界が見えやすい |
| ORM / マイグレーション | Prisma 7.9（`@prisma/adapter-pg` ＋ `pg`） | 課題指定 | DB 操作、スキーマ管理、マイグレーション | `schema.prisma` がそのまま DB 設計書になる。SQL を文字列で組み立てないため SQL インジェクションを防げる |
| データベース | PostgreSQL 16 | 課題指定 | プロフィール・実績・スキル・問い合わせ・画像の保存 | 配列型（`technologies`）やバイナリ型（`imageData`）をそのまま扱える |
| 認証 | Firebase Authentication 12（メール＋パスワード） | 課題指定 | 管理者の本人確認 | パスワードの保管・照合を自前で実装しなくてよい |
| サーバー側の認証・認可 | Firebase Admin SDK 14 ＋ `httpOnly` セッション Cookie（5日間）＋ 管理者 UID の照合 | 課題指定 | ID トークンとセッションの検証、管理者かどうかの判定 | Cookie を `httpOnly` にすることで、画面上のスクリプトからセッションを読めないようにする。管理者は1人なので、権限テーブルを作らず UID の一致で判定する |
| 管理 API の保護 | 内部 API キー（`x-internal-api-key` ヘッダー） | 選択 | Next.js サーバー以外から Express の管理 API を呼べないようにする | Express は Firebase のセッションを知らないため、サーバー同士だけが知る共有キーで守る |
| 画像の保存 | PostgreSQL の `Bytes` 型（`imageData`）＋ `imageMimeType`。JPEG／PNG／WebP、1MB 以下 | （§6 で確認） | プロフィール画像・作品画像 | 画像をリポジトリに置かずに済み、ストレージサービスを別に用意しなくてよい |
| 入力チェック | 自作の検証関数（`backend/src/validation/`、`frontend/src/lib/admin-form-validation.ts`） | 選択 | ブラウザ・Server Action・Express の3段階で検証 | 検証ライブラリを追加せず、何を確認しているかをコードで直接読める |
| テスト | Vitest 4 | 選択 | 入力チェックの単体テスト（フロント・バック各1ファイル） | （§6 で確認） |
| Lint | ESLint 9（フロント：`eslint-config-next`／バック：`typescript-eslint`） | 選択 | コードの問題の検出 | フレームワーク標準の設定を使う。Formatter（Prettier）は未導入（§5） |
| 開発用サーバー | `tsx watch`（バック）、`next dev`（フロント） | 選択 | 保存時の自動再起動 | ビルドなしで TypeScript を実行できる |
| コンテナ | Docker Compose（PostgreSQL のみ） | 選択 | 開発用 DB の起動 | PC に PostgreSQL を直接入れずに、同じバージョンの DB を再現できる |
| パッケージ管理 | npm | 選択 | 依存パッケージの管理 | Node.js に標準で付属する |
| ホスティング | フロント：Vercel／API：Render／DB：Neon | **予定** | 本番公開 | いずれも無料枠があり、Git 連携と自動 HTTPS に対応している |

## 3. 比較サマリ

| 論点 | 採用 | 不採用 | 判断根拠 |
| ---- | ---- | ------ | -------- |
| フロント／バック構成 | 分離（Next.js ＋ Express）。ブラウザは Express を直接呼ばない | Next.js だけで完結（Route Handler から直接 Prisma） | 課題要件。Next.js を間に挟むことで、内部 API キーと DB 接続情報をサーバー側に閉じ込められる |
| 管理 API の守り方 | 内部 API キー | Express 側でも Firebase のトークンを検証する | 認証の判定を Next.js の1か所（`require-admin.ts`）に集められる。Express には Firebase の認証情報を置かなくてよい |
| 未認証時の応答 | HTTP 404 | ログイン画面へリダイレクト／HTTP 401・403 | 課題要件。管理画面が存在すること自体を外部に知らせない |
| 管理者の判定 | 環境変数の UID と一致するか | DB に権限テーブルを持つ | 管理者は本人1人だけのため、テーブルを増やす必要がない |
| 画像の保存先 | PostgreSQL（`Bytes`） | Firebase Storage などのストレージ、`public/` に置く | 管理画面から差し替えられ、外部サービスを増やさずに済む。件数が少なく 1MB 上限なので DB の負担は小さい |
| 入力チェック | 自作の関数 | Zod、express-validator | 項目数が少なく、追加の学習なしで処理を追える |

## 4. リスクと対応

| 技術 | 懸念点 | 対応 |
| ---- | ------ | ---- |
| Firebase Admin SDK | `applicationDefault()` で初期化しており、PC 上の鍵ファイルを前提としている。Vercel には鍵ファイルを置けない | 本番では環境変数（プロジェクト ID・クライアントメール・秘密鍵）から `cert()` で初期化するように変更する。**デプロイ前に必要なコード変更** |
| Firebase Authentication | 本番のドメインが承認済みドメインに入っていないとログインできない | Vercel の URL を Firebase Console の承認済みドメインへ追加する |
| お問い合わせフォーム | 送信回数の制限がなく、公開後に大量送信されると `Contact` テーブルが埋まる | レート制限（IP 単位）や送信間隔の制限を追加する。対応方法は未決定 |
| Express（公開後） | 公開 API は URL を知っていれば誰でも直接呼べる | Express 側でも同じ入力チェックをしているため不正値は拒否できる。管理 API は内部 API キーで保護。`helmet` の導入を検討 |
| 内部 API キー | 文字列を `!==` で比較している | `crypto.timingSafeEqual` での比較に変える（優先度は低い） |
| 画像（DB 保存） | `Cache-Control: no-store` のため、表示のたびに DB から読み出す | 件数が少ないため現状は許容。遅い場合はキャッシュの設定を見直す |
| Render 無料枠 | 一定時間アクセスがないと停止し、次の表示が遅くなる | 応募先へ URL を送る前に一度開いておく。`/health` で起動を確認できる |
| Neon 無料枠 | 休止からの復帰に時間がかかることがある | 初回の遅延は許容する。マイグレーションはプールを通さない接続文字列で実行する |
| Node.js のバージョン | リポジトリ内で固定していない（`.nvmrc`・`engines` なし） | 本番と開発で同じバージョンになるよう固定する |
| 品質確認 | CI がなく、lint・テスト・ビルドは手動で実行している | GitHub Actions の導入を検討（§5） |
| ログ | `console.error` のみで、本番と開発の出し分けがない | 問い合わせの本文やメールアドレスを直接出力する箇所はない（エラーオブジェクトのみ出力）。出し分けは必要になった時点で検討 |
